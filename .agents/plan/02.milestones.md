# Roadmap: Prototype to a Full Go Statistical-Analysis Library

The current prototype is a strong **one-way ANOVA arithmetic core** with a docs-first specification. The path to a broader statistical library should remain **layered and evidence-gated**: each new analysis family needs a defined estimand, numerical algorithm, reference oracle, API contract, and test corpus before it is added.

## Phase 0 — Make the prototype buildable and independently verifiable

**Goal:** turn the current source into a tested, reproducible Go module.

### Next step: validated F-distribution / p-value integration

This is the immediate planned work item.

1. **Choose a module identity**
   - Replace the placeholder module path `example.com/anova`.
   - Select the repository location, versioning strategy, and license.

2. **Set up a Go-capable CI environment**
   - Pin a supported Go version.
   - Run formatting, compilation, unit tests, fuzzing, and race tests where relevant.
   - Add a reproducible CI workflow.

3. **Run the Gonum distribution spike**
   - Identify the exact Gonum package/API for the F-distribution survival function or a regularized incomplete-beta primitive.
   - Pin the Gonum version in `go.mod`.
   - Verify behavior for invalid parameters, zero, finite F statistics, large F statistics, and positive infinity.

4. **Ingest independent oracle fixtures**
   - Generate fixed ANOVA-table and F-tail fixtures using pinned R and SciPy versions.
   - Record tool versions, scripts, tolerances, source URLs, and checksums in `references/`.
   - Keep normal CI fully offline: tests consume checked-in fixtures rather than invoking R or Python dynamically.

5. **Enable `Result.P`**
   - Implement an internal F-tail adapter.
   - Populate p-values only for valid finite and infinite-F states.
   - Retain `NaN` for invalid or indeterminate states.
   - Differential-test every F-tail fixture against R and SciPy.

**Exit criteria:** the current batch and append-only streaming one-way ANOVA implementation compiles and passes its arithmetic, edge-case, p-value, differential, fuzz, and race-validation gates.

## Phase 1 — Release-quality one-way ANOVA

**Goal:** make the initial narrow library safe to use in production analysis workflows.

### Deliverables

- Stable public API and semantic-versioning policy.
- Complete GoDoc, examples, and package-level assumption warnings.
- Typed, documented result statuses and errors.
- Benchmark suite for:
  - ingestion throughput;
  - snapshot latency by number of groups;
  - merge performance;
  - memory allocation behavior.
- Release notes explaining:
  - ordinary one-way ANOVA assumptions;
  - append-only streaming semantics;
  - merge disjointness requirement;
  - repeated-snapshot / optional-stopping warning;
  - unsupported analysis types.

### Quality gates

- Batch, sequential stream, and partition-merge results agree within documented tolerances.
- Large-offset fixtures confirm that centered moments prevent raw-sum cancellation failures.
- Invalid inputs and numerical overflow paths are atomic.
- API ownership is clear: no mutable internal state leaks through results.
- Public docs distinguish **statistical computation** from **valid study design and interpretation**.

## Phase 2 — Core descriptive-statistics foundation

**Goal:** create reusable primitives that support all later models without duplicating numerical logic.

### Add a `stats` foundation package

- Counts, finite-value validation, and missing-value policies.
- Numerically stable:
  - mean;
  - variance and standard deviation;
  - covariance and correlation;
  - min/max;
  - quantiles and robust summaries;
  - online/mergeable moments.
- Weighted-summary primitives, specified separately from the unweighted ANOVA core.
- Distribution abstraction layer:
  - normal;
  - t;
  - chi-square;
  - F;
  - optionally beta and gamma.
- Confidence intervals for basic descriptive measures.

### Design principle

The library should separate:

1. **Accumulation** — stable sufficient statistics;
2. **Estimation** — point estimates, standard errors, intervals;
3. **Inference** — test statistics and p-values;
4. **Diagnostics** — assumptions and warnings;
5. **Reporting** — tables, structured result objects, export adapters.

This prevents ANOVA-specific logic from becoming the accidental foundation for unrelated analyses.

## Phase 3 — Common hypothesis tests

**Goal:** cover the most common univariate inference workflows with coherent result semantics.

### Candidate tests

| Family | Initial methods | Required design choices |
|---|---|---|
| Mean comparisons | One-sample t-test, paired t-test, two-sample pooled and Welch t-tests | One- vs two-sided alternatives, paired-data contract, unequal-variance behavior |
| Proportions | One- and two-sample proportion tests | Exact versus asymptotic path, small-count rules |
| Variances | Levene/Brown–Forsythe-style diagnostics, possibly Bartlett | Robustness and normality assumptions |
| Nonparametric | Mann–Whitney, Wilcoxon signed-rank, Kruskal–Wallis | Tie handling, exact/approximate calculation, continuity correction |
| Association | Pearson and Spearman correlation tests | Missing-value and tie policies |
| Categorical | Chi-square and Fisher exact test | Sparse-table thresholds, exact algorithm and limits |

Each test should return a consistent result shape:

- method and alternative;
- estimate and effect direction;
- statistic;
- degrees of freedom where applicable;
- p-value;
- confidence interval where meaningful;
- sample-size and missing-data accounting;
- warnings/status;
- assumptions and reference-method provenance.

## Phase 4 — Complete the ANOVA family

**Goal:** evolve from classical one-way ANOVA into a well-specified family rather than a collection of similarly named functions.

### 4.1 Welch one-way ANOVA

Add unequal-variance one-way ANOVA as a distinct method.

Required work:

- specify the Welch test statistic and denominator degrees-of-freedom approximation;
- define small-group and zero-variance behavior;
- add R/SciPy or other independent reference fixtures;
- decide whether streaming support is exact, approximate, or deferred;
- ensure result names make the model distinction obvious.

### 4.2 Effect sizes and intervals

Add clearly documented estimates such as:

- eta squared;
- omega squared;
- epsilon squared where appropriate;
- confidence interval strategy, if supported.

These must have explicit zero-variance and bias-correction behavior.

### 4.3 Planned contrasts and multiple comparisons

Introduce only after choosing a coherent multiplicity framework:

- planned contrasts;
- pairwise comparisons;
- Tukey HSD;
- Holm, Bonferroni, and false-discovery-rate adjustments;
- simultaneous confidence intervals.

The omnibus ANOVA test should remain separate from post-hoc procedures.

### 4.4 Factorial ANOVA

Move from direct one-way arithmetic to the general linear-model framework:

- two-way and higher-factor designs;
- interactions;
- balanced and unbalanced designs;
- Type I, Type II, and Type III sums of squares;
- contrast coding;
- rank deficiency and estimability behavior.

This is the point at which ANOVA should be implemented primarily as a **linear-model result**, not through increasingly specialized direct formulas.

### 4.5 Repeated measures and mixed models

Treat these as a separate modeling family:

- subject identifiers and within-subject factors;
- covariance/sphericity assumptions;
- corrections or mixed-effects alternatives;
- incomplete/repeated observation handling.

Do not fold repeated-measures data into ordinary independent-groups ANOVA.

## Phase 5 — Linear-model engine

**Goal:** establish a general regression platform that supports ANOVA, ANCOVA, generalized tests, and model diagnostics.

### Core capabilities

- Design-matrix construction.
- Formula or explicit-matrix API.
- Categorical encoding and contrast specification.
- QR decomposition as the default least-squares path.
- SVD fallback for rank-deficient models.
- Coefficients, fitted values, residuals, leverage, standard errors, covariance matrix.
- Nested-model comparison.
- ANOVA tables derived from model comparisons.
- Robust covariance estimators as separately labelled options.
- Prediction APIs and confidence/prediction intervals.

### Statistical requirements

- Explicit missing-data policy.
- Rank-deficiency and aliased-coefficient reporting.
- Reproducible factor-level ordering.
- Diagnostics:
  - residual summaries;
  - leverage;
  - influence;
  - heteroscedasticity indicators;
  - normality-oriented residual diagnostics.

This phase unlocks **ANCOVA**, factorial ANOVA, regression, and many generalized analysis patterns.

## Phase 6 — Generalized models and resampling

**Goal:** support non-Gaussian outcomes and assumption-robust inference.

### Generalized linear models

Potential initial models:

- logistic regression;
- Poisson regression;
- binomial models;
- negative-binomial models, if overdispersion requirements justify it.

Required infrastructure:

- iteratively reweighted least squares or another specified optimizer;
- convergence diagnostics;
- separation and boundary warnings;
- likelihood, deviance, and information criteria;
- robust standard-error strategy;
- model-comparison semantics.

### Resampling and permutation methods

- Bootstrap confidence intervals.
- Permutation tests.
- Randomization-test framework.
- Cluster-aware or paired resampling units.
- Reproducible random-number-generation policy.

Resampling is valuable because it offers a route to analysis under weaker distributional assumptions, but its units, exchangeability conditions, and computational budget must always be explicit.

---

## Phase 7 — Streaming and distributed analytics expansion

**Goal:** extend streaming only where the statistical semantics remain valid.

### Safe extensions

- Mergeable descriptive statistics.
- Group summaries.
- Online one-way ANOVA snapshots.
- Distributed partition merges.
- Approximate quantile sketches, clearly labelled as approximate.

### Features needing separate specifications

| Feature | Why it requires a new design |
|---|---|
| Dynamic groups | Changes schema, degrees of freedom, ordering, and merge compatibility |
| Weighted streaming ANOVA | Changes sufficient statistics and estimand |
| Sliding windows | Requires deletions, event time, expiry, late-event handling, rebuild policy, and numerical reconciliation |
| Sequential testing | Requires alpha spending, confidence sequences, or another always-valid approach |
| Drift detection | Is not ordinary hypothesis testing and needs a detection-performance framework |
| Online regression | Requires a separate numerical update and regularization/rank policy |

The library should never label an append-only snapshot test as a sequentially valid monitoring method unless it implements one.

## Phase 8 — Data interfaces, reporting, and interoperability

**Goal:** make the library practical without coupling the mathematical core to a single data ecosystem.

### Interfaces

- Slice and iterator APIs.
- Columnar-table adapters.
- CSV/JSON data adapters in a separate package.
- Optional Apache Arrow integration.
- Data-frame adapters only as optional integrations.

### Reporting

- Structured result objects as the canonical interface.
- Text table renderer.
- JSON serialization with schema versioning.
- Markdown/HTML reporting adapters.
- Reproducibility metadata:
  - library version;
  - analysis specification;
  - input schema;
  - missing-data behavior;
  - random seed;
  - warnings and numerical statuses.

---

## Phase 9 — Reliability, governance, and release engineering

**Goal:** make it trustworthy in regulated or high-consequence analytic workflows.

### Engineering standards

- Semantic versioning and deprecation policy.
- Dependency pinning and vulnerability review.
- Deterministic tests and reproducible benchmark data.
- Fuzzing for numerical/API invariants.
- Performance regression tracking.
- API compatibility testing.
- Cross-platform CI.
- Release signatures/checksums and SBOM generation.

### Statistical governance

- Every supported method has:
  - formal specification;
  - source register;
  - independently generated reference fixtures;
  - edge-case policy;
  - assumptions and interpretation notes;
  - differential tests where external references exist.
- Every approximate method states:
  - approximation type;
  - error/accuracy target;
  - fallback behavior;
  - memory and time complexity.

# Recommended sequencing

## Near term

1. **Phase 0:** validated Gonum p-value path and independent R/SciPy fixtures.
2. **Phase 1:** release-quality one-way ANOVA.
3. **Phase 2:** reusable descriptive statistics and distribution foundation.
4. **Phase 3:** t-tests, nonparametric tests, correlations, contingency-table tests.
5. **Phase 4:** Welch ANOVA, effects, contrasts, multiplicity, then factorial ANOVA.
6. **Phase 5:** general linear models and ANCOVA.
7. **Phase 6–9:** generalized models, resampling, streaming extensions, integrations, and governance.

## Strategic rule

Do **not** expand by adding named tests opportunistically. Add a method only after its:

- statistical contract,
- numerical implementation strategy,
- reference behavior,
- degenerate-input rules,
- test oracle,
- documentation,
- and public result semantics

are all defined.
