# Open Questions

## How should we deal with NaNs and Infs?

`Result` contains `float64` fields (`F`, `P`, `BetweenMS`, `WithinMS`) that are
legitimately non-finite in normal operation:

- `P` is **always `NaN`** — no F-tail adapter is validated yet
- `F` is **`+Inf`** when `StatusInfiniteF` (within-SS is zero, between-SS is not)
- `BetweenMS`, `WithinMS` start as `NaN` and may remain so for non-OK statuses

`encoding/json` rejects non-finite `float64` per the JSON spec, so
`json.Marshal(result)` currently returns an error for every `Result` the library
produces. This is documented in `TestJSON_Result_NaNInfLimitation`.

The workaround today: serialize `Groups []GroupSummary` only, which is the
sufficient state and contains no non-finite values.

### Options to consider

| Option | Trade-off |
| ------ | --------- |
| Emit `null` for NaN/Inf via custom `MarshalJSON` on `Result` | Standard JSON, loses distinction between "not computed" and "truly zero" |
| Emit string sentinels `"NaN"`, `"+Inf"` | Non-standard; breaks consumers expecting numbers |
| Separate `TableJSON` / `TableProto` view type with nullable fields | Clean API boundary, more types to maintain |
| Pointer fields (`*float64`) with `nil` for NaN/Inf | Idiomatic Go nullable, changes the struct shape callers already use |
| Keep as-is; only `Groups` is the persistence contract | Simplest — callers who need JSON of the full table write their own view |

### Related questions

- Once `P` has a real value (after F-tail adapter lands), is `NaN` still the
  right sentinel for "not computed" or should `Status` carry that signal alone?
- Should `F = +Inf` be a numeric value in JSON, or does it need a status-only
  representation?
- Does the `Load([]GroupSummary)` API (not yet implemented) change what needs
  to be serializable?
